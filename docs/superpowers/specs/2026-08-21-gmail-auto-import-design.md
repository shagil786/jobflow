# Gmail automatic import and evidence-driven classification

## Summary

JobFlow will replace the current manual `JobFlow/Track` label requirement with an automatic, user-authorized mailbox backfill. The product will scan Gmail metadata and bounded snippets within a user-selected history range, prioritize the newest one-day window, then process older mail in seven-day batches through a durable SQS-compatible queue. A deterministic filter will reduce the candidate set before any AI enrichment. Uncertain results will remain in a review queue; only user-confirmed evidence can create or update applications, timelines, reminders, or contacts.

The default history range is two months. Users can extend it from Settings. The initial request is asynchronous and returns a durable backfill run. The dashboard shows first-day results as soon as they are ready while the remaining batches continue in the background.

## Decisions and architecture

### Ingestion and orchestration

- Gmail OAuth remains read-only. JobFlow does not create labels, move messages, modify Gmail filters, or send mail during import.
- A backfill run has one-day priority batch followed by seven-day date-window batches. Each batch has an explicit inclusive start/exclusive end time, status, attempt count, checkpoint, counts, timestamps, and safe failure code.
- The ingestion service publishes batch jobs to AWS SQS in production and LocalStack SQS locally. A dedicated dead-letter queue receives exhausted jobs. Consumers use visibility timeouts, bounded retries with backoff, and idempotent message processing.
- The queue payload contains only identifiers and window metadata: tenant ID, user ID, connection ID, run ID, batch ID, correlation ID, attempt ID, and date window. It never contains OAuth tokens, raw email bodies, resumes, or AI prompts.
- A run can be paused, resumed, cancelled, or extended. Pause prevents new work from being claimed; an in-flight batch completes or safely retries. Cancel prevents future batches and marks unfinished work cancelled without deleting imported evidence.
- The existing incremental Gmail history cursor remains the path for future sync after the initial backfill. Cursor updates happen only after a page's metadata has been persisted successfully.
- The existing label-scoped mode remains available as an optional advanced filter, but it is no longer required for the normal onboarding flow.

### Message pipeline

1. List messages in the batch date window using Gmail query/date bounds and pagination.
2. Fetch metadata only: message ID, thread ID, sender, reply-to, recipients, subject, date, labels, and bounded provider snippet where available.
3. Deduplicate by `(connection_id, provider_message_id)` and maintain thread identity separately from application identity.
4. Apply deterministic signals: recruiter/company domains, application/interview/rejection/offer language, reply direction, calendar/interview terms, unsubscribe/promotional signals, and known non-job categories.
5. Store a redacted evidence record and candidate score. Messages below the candidate threshold remain excluded from AI processing but remain represented in aggregate scan counts.
6. Fetch bounded body content only for candidates requiring context. Sanitize HTML, cap decoded content, hash processed content, avoid attachments, and delete raw processing content after the configured short retention period.
7. Run the provider-neutral classifier. Azure OpenAI is the first adapter; AWS Bedrock is a supported alternative selected by configuration/feature flag. The classifier must return structured fields, confidence, evidence spans, missing fields, and a `requiresReview` decision.
8. Persist a versioned classification suggestion. No suggestion changes a confirmed application until the user accepts it.

### Identity and follow-up rules

- A confirmed application requires company and role. If either is missing, the suggestion remains reviewable and cannot create a confirmed application.
- Company and role candidates must include source evidence. Sender-domain inference is a candidate, never proof; generic providers and forwarding addresses produce an unknown company candidate.
- Email threads and applications are separate entities. Multiple threads may map to one application only after matching evidence and user confirmation.
- Follow-up recommendations are generated by transparent rules using message direction, latest meaningful inbound/outbound event, known application status, and elapsed time. AI may summarize why a recommendation exists, but it cannot silently schedule it.
- The user confirms or edits the follow-up date. A follow-up is suppressed when the thread has a newer unanswered outbound message, an explicit rejection/closure, an offer, or an active interview event unless the user overrides it.
- Draft generation remains editable and unsent. It must check recipient confidence, existing outreach, Gmail thread, application status, selected resume, and unsupported claims before creating a Gmail draft.

## API contracts

The web application remains the authenticated boundary for the browser. It proxies tenant-scoped requests to ingestion-service using the existing internal service authentication. Public browser routes use `/api/gmail/*`; service contracts use `/internal/v1/gmail/*` and versioned resource names.

### Start a backfill

`POST /api/gmail/backfills`

Headers: authenticated session, `Idempotency-Key`, `X-Correlation-Id`.

Request:

```json
{
  "from": "2026-06-21T00:00:00Z",
  "to": "2026-08-21T00:00:00Z",
  "mode": "automatic",
  "batchSizeDays": 7,
  "includeSnippets": true
}
```

Rules:

- `from` and `to` must be valid UTC instants, `from < to`, and the range must not exceed the configured plan/fair-use limit.
- Omitted dates use the account's saved setting, defaulting to the previous two months ending now.
- `batchSizeDays` is fixed to seven for normal clients; the server rejects unsupported values.
- A second active backfill for the same connection returns `409 GMAIL_BACKFILL_ALREADY_ACTIVE` unless the request is the same idempotency key.

Response: `202 Accepted`, `Location: /api/gmail/backfills/{runId}`.

```json
{
  "data": {
    "runId": "uuid",
    "status": "queued",
    "priorityBatch": { "from": "...", "to": "...", "status": "queued" },
    "totalBatches": 10,
    "completedBatches": 0,
    "totalMessages": 0,
    "candidateMessages": 0,
    "reviewItems": 0,
    "requestedFrom": "...",
    "requestedTo": "..."
  }
}
```

### Read and control a backfill

- `GET /api/gmail/backfills/{runId}` returns the run, current batch, progress counts, latest safe failure, stale-data warning, and `allowedActions`.
- `POST /api/gmail/backfills/{runId}/pause` returns `202` and moves the run to `pausing`/`paused`.
- `POST /api/gmail/backfills/{runId}/resume` returns `202` and republishes pending/retryable batches.
- `POST /api/gmail/backfills/{runId}/cancel` returns `202` and prevents future work.
- `POST /api/gmail/backfills/{runId}/extend` accepts an earlier `from` date and prepends non-overlapping seven-day batches. It requires explicit user confirmation in the UI.

Run statuses are `queued`, `running`, `paused`, `pausing`, `cancelling`, `completed`, `completed_with_warnings`, `failed`, and `cancelled`. Batch statuses are `queued`, `running`, `succeeded`, `retrying`, `dead_lettered`, `paused`, `cancelled`, and `skipped`.

### Review queue

- `GET /api/gmail/review-items?cursor=&limit=` returns cursor-paginated suggestions scoped to the current user and connection.
- `POST /api/gmail/review-items/{suggestionId}/accept` accepts the suggestion with optional corrections for company, role, status, contact, and application date.
- `POST /api/gmail/review-items/{suggestionId}/dismiss` records a dismissal reason and prevents the same suggestion version from resurfacing.
- `POST /api/gmail/review-items/{suggestionId}/correct` records a correction and creates a new classifier evaluation sample.

All mutating endpoints require idempotency keys. Errors use the standard envelope `{ "error": { "code": "...", "message": "...", "details": {} } }`; production responses never contain stack traces, raw provider responses, email bodies, prompts, or tokens.

## Persistence and security

Add Flyway migrations for:

- `gmail_backfill_runs` with tenant/user/connection ownership, requested range, status, counters, timestamps, and idempotency key.
- `gmail_backfill_batches` with run ownership, date window, sequence, status, queue receipt/checkpoint, attempts, counts, and safe failure metadata.
- `gmail_message_candidates` with deterministic score/signals, processing state, classifier version, and retention timestamps.
- `gmail_review_items` or an equivalent versioned link from suggestions to backfill/candidate evidence.
- Unique constraints for tenant-scoped idempotency and provider message identity; indexes for active runs, queued batches, connection/date window, and review ordering.

Every read and write enforces tenant ID and user ID at the service boundary and repository query. SQS payloads are signed or authenticated through the service's queue credentials. OAuth refresh tokens remain encrypted. Raw message content is not logged, traced, sent through queue payloads, or retained beyond the configured processing window. Export and account deletion must include runs, batches, candidates, suggestions, and evidence metadata.

## Frontend experience

The dashboard uses the selected quiet-background hierarchy:

- Today remains action-first and shows confirmed next actions, not unreviewed guesses.
- A compact expandable import status surface shows current state, first-day readiness, batch progress, counts, last successful sync, and safe recovery actions.
- The first-day completion state links directly to the review queue and confirmed applications. It does not claim the entire mailbox is processed.
- The review queue clearly separates “Likely job-related” from “Needs more context,” shows sender/subject/date/evidence, and provides Accept, Correct, Dismiss, and Open Gmail actions.
- Settings includes history range, automatic sync mode, optional label filter, privacy/retention controls, pause/resume, and extend-history action.
- All data-dependent surfaces implement loading skeleton, empty, partial-sync, stale, retryable error, completed-with-warnings, and offline/reconnect states.
- At 320px, progress controls stack without horizontal overflow. Keyboard focus, accessible names, reduced motion, and color-independent status indicators are required.

## Testing and acceptance

Backend tests must cover:

- Date-window generation: one priority day followed by non-overlapping seven-day windows.
- Idempotent run creation and conflict on a second active run.
- Tenant/user isolation for runs, batches, messages, suggestions, and controls.
- SQS publish, visibility timeout retry, duplicate delivery, pause/resume, cancellation, and DLQ recovery.
- Gmail pagination, rate limits, token expiry, history cursor recovery, malformed metadata, and partial batch failure.
- Deterministic candidate filtering, bounded-body retention, HTML sanitization, provider adapter selection, evidence/confidence output, and unknown-company behavior.
- Review accept/correct/dismiss transitions and application creation only after valid confirmation.
- Follow-up rule calculations, suppression conditions, user rescheduling, and duplicate outreach detection.
- Consistent `202`, `409`, `422`, `429`, and structured error responses.

Frontend tests must cover:

- Start/poll/control flows with stale data and partial completion.
- Quiet status surface expansion and recovery actions.
- Review queue accept/correct/dismiss behavior and optimistic update rollback.
- Empty, loading, error, completed-with-warnings, and offline states.
- 320px and desktop layouts, keyboard navigation, focus management, screen-reader labels, and reduced-motion behavior.

Acceptance requires a real Gmail OAuth connection, a real date-bounded backfill against Gmail test data, observable queue/run progress, persisted metadata, reviewable evidence, and no demo/fallback records. A successful build alone is insufficient; API tests, service tests, and browser verification must all pass.

## Explicit non-goals

This change does not add automatic sending, automatic applications, Gmail mutations, mass outreach, LinkedIn scraping, Outlook support, public referral profiles, or autonomous classification that bypasses human review. Those remain separate feature-gated decisions.
